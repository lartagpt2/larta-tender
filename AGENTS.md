# Larta Tender — инструкции Codex

## Назначение и границы

- Разрабатывать **только** тендерную платформу в существующем утверждённом репозитории и выделенной ИТ рабочей области. Перед работой определить реальный корень репозитория через `git rev-parse --show-toplevel` и сверить с человеком. Не принимать `D:\ai_projects` за уже проверенный путь.
- Не выходить за границы рабочей области, не сканировать другие диски, домашние папки, системные каталоги, чужие проекты, продуктивные БД и сетевые ресурсы.
- `AGENTS.md` сам по себе не создаёт ОС-изоляцию. Её наличие должен подтвердить ИТ-администратор через права ОС, сеть и конфигурацию агентной среды.
- Не менять `main` напрямую, не делать force push. Создавать task branch, минимальный diff, PR и handoff.

Frontend: Vue 3 / TypeScript / Vite / PrimeVue 4 / PrimeIcons / Vue Router / TanStack Vue Query / VeeValidate / Zod.

Backend: Node.js / TypeScript / NestJS 11 / Fastify 5 / PostgreSQL / class-validator / class-transformer / AJV / OpenAPI.

Testing: Vitest, Playwright, Jest. Версии пакетов закреплять в lockfile; поддерживаемость согласовать с ИТ.

## Последовательность работы

1. Прочитать текущую задачу полностью, осмотреть существующие файлы, конфигурации и тесты.
2. Зафиксировать увиденное и расхождения с заданием; для существенных изменений предложить короткий план.
3. Не удалять/перезаписывать существующие изменения; соблюдать уже принятые решения и миграции.
4. Реализовать строго в границах одной задачи. Изменения схемы БД — только версионируемой миграцией; применять её к существующей БД лишь после явного подтверждения владельца тестовой среды.
5. Проверить код тестами и вручную по сценариям, записать **фактически выполненные** команды и результат.
6. Создать `handoffs/TASK-NNN.md`, приложить тестовые доказательства, ограничения и список рисков.
7. Не продолжать на следующую задачу без приёмки текущей.

## Безопасность и данные

- Запретить отправку реальных ТЗ, КП, реквизитов контрагентов, персональных данных и секретов во внешнюю модель или сервис. Демо и тесты — только синтетические/обезличенные данные.
- Не писать `.env`, реальные пароли, токены, дампы БД и бинарные КП в Git; использовать `.env.example` с заглушками. Не выводить секреты в логи и handoff.
- Для Ollama использовать локальную конфигурацию, согласованную с ИТ; модель `qwen3-vl:8b-instruct` — выбранный кандидат, не утверждение о проверенном качестве.
- Входящие ZIP/MSG/EML/PDF и другие файлы считать недоверенными; необходимы проверка размера/типа, защита от path traversal и zip bomb, антивирусный шлюз по требованиям ИБ, изоляция OCR.
- Не подключать новые MCP, внешние API, GitHub Actions с широкими полномочиями, доступы 1С или почтовую отправку без отдельного одобрения.
- Не менять разрешения пользователей, системные настройки, firewall или службы.

## Функциональные инварианты

- Оригинал КП неизменяем; пользовательские правки и все версии цен сохраняются отдельно с источником и автором.
- Распознавание LLM никогда не равно подтверждению закупщиком. Отсутствующая информация явно отображается как отсутствующая, а не как ноль.
- Изначальная стоимость КП неизменна. Каждый этап/переторжка добавляет строку в **ту же** транспонированную сравнительную таблицу. Нет ответа — действует последняя подтверждённая цена; скидка этапа рассчитывается отдельно.
- Сравнение по лоту или позициям выбирает закупщик. Доп. затраты добавляются по отдельной галочке и учитываются без двойного счёта.
- Если нет загруженного отчёта аккредитации поставщика, статус в сравнении красный: «Нет проверки».
- Письма — черновики до явного подтверждения человеком; автоматическая отправка не входит в MVP.
