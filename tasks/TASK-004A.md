# TASK-004A — Извлечение состава тендера из текстового PDF-ТЗ

**Проект:** Larta Tender · дополнение после TASK-004  
**Дата:** 06.11.2026  
**Приоритет:** P0, блокирует практическую проверку загрузки ТЗ  
**Статус:** постановка задачи; код локального Codex пока не проверен

## 1. Наблюдение и причина для проверки

При загрузке ТЗ пользователь увидел сообщение: «Загрузите оригинал ТЗ. Автоматическая обработка пока недоступна; загруженный файл не подтверждает состав закупки». Состав не появился.

В текущем плане TASK-004 регистрация файла не означала реального OCR. Однако конкретный приложенный PDF **содержит извлекаемый текст**: стандартное извлечение `pdftotext -layout` показывает семь пронумерованных позиций и количество. Таким образом, для этого документа не нужна визуальная LLM; достаточно server-side извлечения текста PDF и детерминированного разбора с подтверждением закупщиком.

**Не утверждать без изучения репозитория**, что ошибка вызвана конкретным файлом/методом: сначала выяснить, какой handler и статус реализованы в TASK-004. Не заменять работающие части системы без необходимости.

## 2. Бизнес-результат

После загрузки текстового PDF-ТЗ система:

1. Сохраняет оригинальный файл без изменений и контрольную сумму SHA-256.
2. Извлекает текст с разбивкой по страницам.
3. Показывает закупщику черновик состава лота: наименование, количество, единица, номер и страница-источник.
4. Извлекает технические условия в отдельные группы/примечания, связывает их с соответствующими позициями.
5. Разрешает исправить и подтвердить черновик; **до подтверждения** статус не «состав подтверждён».
6. После подтверждения сохраняет LotItem в PostgreSQL и включает сравнение по позициям.
7. Не создаёт ложных позиций из реквизитов, подписей, описаний покрытий и таблицы версий документа.

## 3. Минимальная реализация

- В backend сделать отдельный `PdfTextExtractionService` на поддерживаемой, согласованной с ИТ библиотеке/утилите. Проверять фактический PDF по сигнатуре, страницы, размер и лимиты обработки.
- `extractText(file) -> {pages: [{page, text}], hasText, diagnostics}` с обработкой ошибок. Текст сохраняется как производный артефакт с указанием исходного документа; не заменяет оригинал.
- Для обычного текстового PDF использовать структурный парсер списков (номер `1.`/`6.`, перенос строки, тире `–`/`-`, количество + `шт.`/`шт`, возможные пробелы); сохранить полное наименование без потери технического артикула и ведущих цифр.
- Для сканированного PDF/пустого извлечения вернуть `needs_ocr`, **не выдумывать позиции**; последующим этапом направлять в локальный Ollama/Qwen3-VL только после отдельной задачи и утверждения инфраструктуры.
- Поля с низкой определённостью отдавать на ручное уточнение. Количество по умолчанию не ноль, отсутствующие значения `null`.
- Не затрагивать пакеты КП, уже подтверждённые тендеры, аккредитацию и исторические версии.
- Подтверждение через отдельную операцию с проверкой прав и AuditEvent; повторный запуск извлечения не должен перезаписывать подтверждённый состав.

### Технические требования, которые нельзя потерять

- **Позиции 1–5:** корд — стальной; ширина 32 мм; на зубчатой стороне специальная полиамидная (нейлоновая) ткань `NFT, PAZ`; с обратной гладкой стороны — ПВХ с текстурой `Supergrip / Longitudinal ribs`.
- **Позиции 6–7:** корд — стальной; ширина 32 мм; покрытие `PAZ / PAR` — полиамидная ткань на зубчатой и наружной сторонах.
- Визуальные иллюстрации ремней — часть ТЗ, однако в этом задании их OCR не требуется; связь с исходной страницей сохранить.

Не превращать строки «Корд», «Ширина», «Покрытие» в дополнительные закупаемые позиции и не объединять разные артикулы в один товар.

## 5. UX

После выбора файла:

1. Статус «Файл загружен → извлечение текста → черновик ТЗ готов».
2. Если текст есть — таблица семи позиций, редактируемые наименования/количество/единица, отдельная секция характеристик по группам, ссылки «Показать фрагмент PDF».
3. Действия «Подтвердить состав», «Исправить», «Загрузить другое ТЗ», «Пропустить и свернуть».
4. Если PDF сканированный/не обработан — честное «Требуется OCR или ручной ввод», без текста о подтверждённом составе.

## 6. Тесты и критерии приёмки

- [ ] Unit: семь позиций из тестового текстового PDF, точные артикулы и количества; сумма `70+40+30+30+30+40+20=260`.
- [ ] Unit: технические требования 1–5 и 6–7 относятся к своим группам и не становятся позициями.
- [ ] Unit: пронумерованный список с переносами, длинными дефисами, `шт` без точки.
- [ ] Unit: скан/пустой текст → `needs_ocr`, без фиктивных позиций.
- [ ] API: после загрузки состав **черновой**, до кнопки подтверждения нет окончательных LotItem.
- [ ] E2E: загрузить ТЗ, увидеть 7 строк, поправить одну строку, подтвердить, обновить страницу; данные сохранены в PostgreSQL.
- [ ] E2E: повторная загрузка того же PDF не дублирует подтверждённый состав и не стирает предыдущую версию.
- [ ] Тестовые данные обезличены; **оригинальный приложенный файл с контактными данными не коммитить в Git**. Для автоматических тестов создать синтетический PDF с тем же устройством перечня, но без реальных контактных данных.
- [ ] Jest/API/Playwright и фактические команды проверки описаны в `handoffs/TASK-004A.md`.
