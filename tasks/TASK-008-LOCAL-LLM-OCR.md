# TASK-008 — Интеграция локальной Ollama / Qwen3-VL для извлечения данных из ТЗ и КП

**Проект:** Larta Tender. **Приоритет:** высокий. **Срок/статус:** к запуску после проверки актуального состояния TASK-007.  
**Цель:** автоматическое формирование **неподтверждённых черновиков** по ТЗ и КП, определение кандидата поставщика и заполнение экрана ручной проверки, без потери оригиналов и истории этапов.

- Прочитать актуальный `AGENTS.md`, `docs/DOMAIN_API.md`, `docs/ACCEPTANCE.md`, `handoffs/TASK-004A.md` (если есть), `handoffs/TASK-005[B].md`, `handoffs/TASK-006.md`, `handoffs/TASK-007.md` (если готов), маршруты загрузки документов, `DocumentProcessingPort`, существующие `field_decision`, `document`, `offer_package`, `offer_version`, `receipt`/историю поступлений и права пользователей. Не угадывать имена таблиц/API: сначала обследовать настоящий код.

Если TASK-007 ещё в работе — **не переписывать её ветку**: после обследования зафиксировать точку интеграции, создать отдельную ветку на согласованной базе или остановиться до готовности зависимостей.

## 1. Gate A — диагностика и согласование окружения (перед реальным inference)

Собрать в безопасный отчёт **без секретов**:

1. ОС, CPU, ОЗУ, GPU и объём VRAM, свободное место и доступность Ollama **только в согласованной рабочей области/через разрешённые штатные средства**. Не сканировать домашние каталоги и чужие диски.
2. `ollama --version`, `ollama list`, доступность `GET /api/tags` по согласованному локальному адресу (обычно `127.0.0.1:11434`). Подтвердить локальность endpoint, исключить cloud model и сетевой proxy. Версии/модель — фактические, не предположительные.
3. Проверить наличие `qwen3-vl:8b-instruct` и способность выполнить **нечувствительный synthetic smoke test**. При отсутствии модели указать команду установки как предложение и дождаться разрешения на загрузку. Проверить совместимость установленной Ollama с моделью, наличие изображения на входе, JSON schema output и таймауты.
4. При нехватке ресурсов предложить меньшую модель только как **альтернативу на согласование**, не заменять выбранную молча. Замерить время обработки 1 тестовой страницы; не обещать скорость заранее.

**Результат Gate A:** `docs/OLLAMA-ENV-REPORT.md` (PASS/BLOCKED по пунктам), рекомендации по конфигурации и явное подтверждение владельца на запуск реального inference. Без разрешения допускается дальше писать тестируемый адаптер с mock, не запускать чувствительные файлы.

## 2. Архитектура: локальный документный конвейер

Предусмотреть поток:

`uploaded original → safe format inspection → native text/table extraction if possible → OCR/vision for raster/scanned pages → JSON draft → validation and provenance → human review/confirmation → existing tender/offer model`.

- Обрабатывать оригинал **только со стороны NestJS**, без пересылки браузером base64 в Ollama. Изолировать адаптер `LocalDocumentAI` за существующим `DocumentProcessingPort` (или согласованным расширением). Конфигурация через `.env.example` (`OLLAMA_BASE_URL`, `OLLAMA_MODEL`, `DOCUMENT_AI_ENABLED=false` по умолчанию, таймаут/лимиты) без секретов/жёстко зашитых абсолютных путей.
- Для текстовых PDF сначала извлекать текст и таблицы детерминированно; для сканов — рендерить страницы локально в изображения с ограничением числа страниц, разрешения, размера памяти и времени. Нельзя передавать PDF непосредственно в vision API в предположении, что это изображение. XLSX — локальный безопасный парсер таблиц после проверки входа. EML — использовать только одобренный текущий парсер с вложениями; MSG и ZIP оставить `unsupported/blocked` до отдельного решения.
- Вызов `POST /api/chat`: text + `images` для vision, `stream:false`, структурированный JSON schema через `format`, ограниченные generation options. Реальную совместимость выбранной версии Ollama проверить smoke test. Схему ответа валидировать Zod/AJV; неизвестные значения = `null`, а не 0/выдуманное значение.
- Каждое поле возвращает `rawValue`, нормализованное `value`, `page`, `sourceDocumentId`, `evidenceSnippet`/местоположение, `confidence` только если обосновано; если модель не даёт калиброванную оценку — не показывать фиктивные проценты. Сохранять model tag/digest (если API предоставляет), schema/prompt version, время, job status, ошибки, source SHA и версию извлечения.
- Защита от prompt injection: текст КП/ТЗ — **недоверенные данные**, содержащиеся в пользовательском документе инструкции не исполнять. Модель не имеет доступа к файловой системе, SQL, отправке почты и инструментам. Не передавать ей учетные данные, системные пути, токены.
- Асинхронная очередь/персистентное задание либо иной restart-safe механизм; этапы `pending/running/completed/needs_review/failed/unsupported`; повторный запуск через явное действие, идемпотентность по оригиналу + конфигурации/версии извлечения, логи без полного текста документа. Поломка Ollama не блокирует ручную работу и скачивание оригинала.

## 3. Функциональные задачи

### 3.1 ТЗ

- Кнопка «Распознать ТЗ» (и по возможности автоматический запуск после загрузки при включённой локальной обработке). Извлекать наименование позиции/оборудования, количество, единицы, технические признаки, отдельные требования и страницы источника.
- Показывать только **черновик**, сопоставлять с уже введённым составом, обнаруживать возможные дубли/противоречия; подтверждать изменения позиций только действием закупщика. Существующий сценарий «Пропустить» и ручной ввод сохраняются.
- Если текстовый PDF уверенно извлечён детерминированным TASK-004A, не ухудшать его качество без проверки; использовать модель лишь для недоступных/спорных фрагментов и нормализации.

### 3.2 КП: поставщик и контакты

- Извлекать **поставщика** отдельно от **покупателя** и **грузополучателя**. Для поставщика: полное/краткое название, ИНН/регистрационный номер, КПП (если есть), номер/дату документа, контакты/почтовый адрес **как указанные в документе**, не как подтверждённый email отправителя.
- Поиск существующего контрагента по нормализованному ИНН/регистрационному номеру и доказуемым реквизитам; имя — кандидат при неоднозначности. Не объединять компании автоматически. Для найденного supplier предлагать ассоциацию с ссылкой на страницу/фрагмент; при неоднозначности оставить «Поставщик не определён» с объяснением и ручным выбором/созданием. **Подтверждение закупщика обязательно** до записи бизнес-связи.
- Адрес, извлечённый из PDF, хранить отдельно от `From` исходного EML. Не утверждать, что email из подписи — адрес фактического отправителя.

### 3.3 КП: позиции и условия

- Извлекать позиционные строки: описание, код/артикул, количество, единицу, цену/ед., сумму, валюту, срок по позиции; итог, НДС, оплату, доставку (включена/дополнительная/неизвестно), срок действия, замечания.
- Сопоставлять позиции с ТЗ как предложения для проверки, показывать несовпадение количества/описания, не делать неутверждённую замену товара и не высчитывать валютные курсы.
- Числа проверять детерминированно: `qty × unitPrice` и сумма строк против заявленного итога, Decimal; при несовпадении/непрочитанном значении `needs_review`.
- Размещать распознанные значения на уже существующем экране S04 «Проверка КП» отдельным слоем, **не перетирать** сохранённые ручные поля, начальную цену, актуальные версии, источники и другие вопросы. Отдельно показывать «Получено из PDF / извлечено ИИ / подтверждено закупщиком».

### 3.4 Этапы тендера

- Загруженное в этапе 2/3/... КП должно получать extraction draft **для конкретного receiptId, supplierId-candidate, lotId и stageId**. Не переносить значения с другого независимого поступления одинаковых байтов, не изменять первоначальную цену или исходную коммерческую версию.
- После ручного подтверждения данные переходят в `OfferVersion` текущего этапа по уже реализованному контракту TASK-007. До подтверждения **не появляется новая действующая цена** в сравнении.
- Сохранить корректный случай «нет ответа»: никакой автоматический переход цены без документа/ручного подтверждения.

## 4. UI и пользовательский сценарий

1. Закупщик загружает PDF КП в общую зону в «Документы», в том числе на втором этапе.
2. У файла отображается «Ожидает распознавания» → «Обрабатывается» → «Черновик готов / Ошибка / Неподдерживаемый формат»; доступна «Повторить обработку» без повторной загрузки оригинала.
3. У готового файла — предложенный поставщик и объяснение (например «Совпадение ИНН в документе с карточкой поставщика»), ссылка на исходную страницу. Не скрывать неопределённость.
4. «Проверить данные» открывает экран со столбцами «В исходном документе / Распознано / Подтверждённое»; закупщик правит поля и выбирает поставщика, лот, поступление, этап.
5. «Сохранить черновик» не изменяет сравнение; «Сохранить и подтвердить» использует существующую проверку обязательных полей/замечаний и только тогда формирует версию предложения. После перезагрузки всё сохраняется.
6. Мобильная версия: статусы видны, форма/таблица не блокируются открытым меню.

Обязательные **синтетические** fixtures (никаких реальных счетов и реквизитов в Git):

- Скан такого же PDF с изображениями вместо текста.
- ТЗ с перечнем оборудования и количествами.
- Второй этап с новым КП того же поставщика и иной ценой; сохранённая первоначальная цена не меняется.
- Два поставщика с общим бинарным оригиналом, два поступления и независимые подтверждения.
- Неполный/битый PDF, неизвестный ИНН, два кандидата по имени, email только в подписи, строка без цены, ошибочная сумма, незнакомая валюта, недоверенная «инструкция» внутри документа, отключённая/недоступная модель.

Пройти Unit (парсинг/схемы/Decimal/сопоставление), интеграционные на реальной **тестовой** БД (с mock Ollama), E2E (без потребности в реальном GPU), **отдельный разрешённый smoke тест** на локальной Ollama и измерение количества корректно извлечённых полей/ошибок на обезличенных документах. Критерии точности и допустимого времени согласовать с владельцем по результатам замеров; не заявлять «100% OCR» или универсальное качество.

## 6. Артефакты и порядок

**Gate A:** отчёт диагностики, предлагаемые зависимости, ресурсы, риски; ожидание разрешения на установку/подключение.

**Gate B:** backend local adapter, parsing, structured extraction, audit, версионированные контракты и тесты; миграции только новые и только с разрешением на применение.

**Gate C:** UI drafts, связь с ТЗ/КП/этапами, права и ручное подтверждение.

**Gate D:** синтетические E2E и сравнение с gold set, затем разрешённая ручная проверка оригинальных документов.

Создать `handoffs/TASK-008.md` с текущей базой Git, commit/PR, изменениями API/схемы, инструкциями запуска Ollama, нагрузочными замерами, фактами PASS/FAIL/BLOCKED/NOT RUN, известными ограничениями и вопросами ИТ/ИБ. Не делать merge и не переходить к следующему заданию до приёмки.

## 7. Критерии приёмки

- [ ] В PDF со счётом/КП распознан именно **поставщик**, а не покупатель; ИНН подтверждается текстом документа, не выдуман.
- [ ] Без ручного ввода названия поставщика система предлагает подтверждаемую связь или честно сообщает о неоднозначности.
- [ ] Из ТЗ предложены состав/количества, но ничего не утверждено автоматически.
- [ ] Из 2-страничного КП предложены все обнаруженные позиции, сроки/цены/итог с проверкой арифметики и ссылками на источники; пропуски явно показаны.
- [ ] КП 2-го этапа обрабатывается в контексте соответствующего поступления/этапа, исходная цена и другие поставщики неизменны.
- [ ] Отключённая/недоступная Ollama не блокирует ручные сценарии и не теряет документы.
- [ ] Ни одна обработка не отправляет документ во внешний LLM/API, не отправляет письма и не утверждает коммерческие условия без человека.
- [ ] Результаты тестов и реальные ограничения отражены в handoff.
