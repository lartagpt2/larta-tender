## 1. P0 — Создание нового поставщика при уточнении КП

**Проблема:** согласно handoff TASK-005, «Уточнить» предлагает только поставщиков, уже связанных с тендером. В новом тендере их может быть ноль; закупщик не может разнести загруженные КП по новым контрагентам.

**Требуемое поведение:**

- В реестре КП действие **«Уточнить» → «Создать нового поставщика»** доступно даже при пустом списке поставщиков.
- Минимально обязательное поле — **наименование**. ИНН/регистрационный номер, email и комментарий — необязательные; отсутствие email не блокирует привязку. Пустые поля не заполнять вымышленными значениями.
- После сохранения поставщик появляется в списке данного тендера; текущий документ можно сразу привязать к нему **одним подтверждённым действием**.
- Записать автора, время и основание ручного решения в журнал; хранить исходные файлы и извлечённые метаданные неизменными. При доступной поддержке группировки вложений разрешить явную привязку всех файлов одной поставки/письма с предварительным показом списка и подтверждением, сохранив отдельные записи решений для каждого документа. Если это требует существенного изменения модели — оформить отдельное предложение, не вводить неявную массовую привязку.
- Не объединять контрагентов автоматически по совпадению названия или email; возможные дубликаты обозначать для ручного решения. Проверить действующие права, валидацию и конфликт ревизий (409).

**Проверки:** тендер без поставщиков → загрузка нескольких документов → создание поставщика → привязка → обновление страницы → корректная группа и аудит; некорректные данные и запрет записи роли-наблюдателю.

## 2. P1 — Безопасный приём ZIP без распаковки

**Проблема:** TASK-005 сейчас полностью отвергает ZIP, хотя закупщик должен иметь возможность загрузить архив КП от поставщика в общее поле.

**Цель:** принимать безопасно ограниченный **оригинальный файл ZIP как единый документ**, показывать его в реестре со статусом **«Архив получен; содержимое не обработано»** и давать скачивать оригинал. **Не распаковывать архив и не создавать фиктивные КП из него.**

- До реализации согласовать с ИТ/ИБ возможность хранения недоверенных архивов без распаковки и политику антивирусного сканирования/карантина. Если согласования нет — оставить текущее отклонение, задокументировать блокер и предложить отдельное решение. Нельзя самовольно объявлять такой приём безопасным для продукции.
- При разрешённом приёме применить текущие лимиты транспортной загрузки и файла; валидировать заявленный тип, расширение и сигнатуру. Установить ограничения обработки без извлечения содержимого; ZIP не открывать на сервере для просмотра.
- В интерфейсе и API различать `received_unprocessed`/эквивалент и подтверждённо разобранный документ. Не показывать содержимое ZIP как распознанное. Предусмотреть место для будущего фонового обработчика, но не включать его.
- ZIP должен группироваться с другими документами и поддерживать ручную привязку к поставщику. Сбой/запрет одного файла не должен терять остальные файлы допустимого пакета; аудит отказов сохраняется.

**Проверки:** разрешённый обычный ZIP + PDF/TXT сохраняются как отдельные оригиналы без распаковки; неправильный тип/превышение лимита отклоняются с понятным сообщением; скачанные байты ZIP совпадают с исходными; после обновления страницы статус не меняется. При отсутствии одобрения ИБ записать эти проверки как `BLOCKED`, не как `PASS`.

## 3. P1 — Разделить дубль файла и повторное поступление КП

**Риск для проверки:** HANDOFF сообщает, что равные байты в одном тендере для purpose=offer не создают новый документ. Это экономит хранилище, но не должно стирать информацию о **новом поступлении** того же файла — например, в очередном этапе тендера.

- Проверить текущую модель `blob` / `document` / `offer_package` / `upload_batch` / `document_relation`: отдельно ли фиксируется факт каждой новой загрузки, дата, источник (email/B2B/ручная загрузка), этап и автор, даже если SHA-256 уже существует.
- **Требование:** хранилище бинарников может дедуплицироваться; новая независимая отправка/поступление должна оставлять отдельное событие или запись поступления с привязкой к тому же оригиналу. Повтор HTTP-запроса с **тем же `Idempotency-Key` и тем же payload** не создаёт новое событие — это повтор одной операции. Новый ключ для нового фактического поступления того же файла создаёт отдельный факт поступления, не дублируя бинарник.
- Сохранить связь с этапом (если он доступен) или явный `stage = не назначен`. Не менять первоначальные цены и не создавать строки сравнительной таблицы в этой задаче.
- Уточнить UI: показывать историю поступлений у файла/группы, не раздувая реестр идентичными дубликатами без объяснения.
- Если текущая модель уже удовлетворяет этому — подтвердить это ссылками на код и автотестом, не делать лишней миграции.

**Проверки:** одинаковые байты + тот же ключ = один приём; одинаковые байты + новый ключ = два факта поступления, один бинарник; разные поставщики или этапы не теряют происхождение файла; перезагрузка сохраняет историю.
