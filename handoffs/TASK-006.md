### Поведение и API

- `GET /api/tenders/:id/verification`: лоты/позиции, поставщики, оригиналы/поступления и отдельные offer/version, текущие замечания.
- `POST /api/tenders/:id/verification/lot`: `{expectedRevision}` создаёт первый лот без позиций только по явному действию. Title-only тендер не вынуждает вводить вымышленную позицию или ТЗ; ревизия/права проверяются, повтор 409.
- `POST /api/tenders/:id/verification`: supplierId, lotId, documentId, receiptId, expectedVersion, contextConfirmed=true, intent=draft/confirm; текущие fields, исходные original при первом сохранении; позиции/расходы; sourceType/sourceNote; newQuestions/resolveQuestionIds.
- `GET /api/tenders/:id/comparison` и `/comparison.csv`: optional lotId, mode=lot/items, itemId. Модель и экспорт формируются на сервере из одних строк и столбцов.
- Валюты текущего MVP: RUB/USD/EUR/CNY. Режимы НДС: included/excluded/unknown. Единицы не конвертируются по неутверждённым коэффициентам; допустима только нормализация регистра/пробелов/конечной точки.
- Для confirm обязательны валюта/оплата/срок и общая цена лота без позиций; при наличии состава итог вычисляется из всех обязательных позиций. Недостающие цены/неуточнённый НДС/соответствие/расход/ручной вопрос оставляют needs_review и блокируют рейтинг.
- Только реально изменённые поля получают новый источник/комментарий/автора/дату. Порядок ключей JSONB не считается изменением. Встроенные замечания пересчитываются сервером; поддельный UUID снятия вопроса отвергается. Другой вопрос не удаляется исправлением срока.
- Дополнительные расходы выключены по умолчанию; add прибавляется один раз при включении учёта, included не прибавляется, unknown не становится нулём. Неизвестный сохранённый расход требует уточнения даже при выключенной галочке.
- По позициям не производится неявное распределение добавляемых расходов лота; такой итог не ранжируется. Разные валюты и базы НДС не получают общего рейтинга, нет FX/НДС-конверсий.
- CSV: UTF-8 BOM, `;`, CRLF, кавычки/экранирование; поля, источники/комментарии, авторы/даты, IDs контекста и SHA. Чистые отрицательные числа сохраняются; потенциально формульный текст защищается апострофом.

## 4. Схема и данные

**Миграций нет.** Применённые 001/002 не редактировались, новые DDL не применялись. Существующая postgres не изменялась; глобальная конфигурация PostgreSQL/службы/PATH/реестр не менялись.

Использованы существующие offer_package/offer/offer_version/offer_item/cost_component/field_decision/audit_event; добавление первого лота использует существующую lot. Скрипты оставили в larta_test_task003 новые синтетические тендеры, пользователей/поставщиков, документы/поступления, предложения/версии, расходы, решения/аудит и один тестовый accreditation_report. Удаление/переписывание старых версий и чужих данных не выполнялось.

### Почему общий оригинал не смешивает контрагентов

1. Загрузочный document.offer_package_id и blob остаются неизменными.
2. Для каждой пары supplier/lot создаётся отдельный offer_package и offer с FK на этот tender/supplier/lot.
3. offer_version принадлежит конкретному offer/package/lot/tender и может ссылаться на общий source_document_id, не заимствуя чужие поля.
4. Решение field_decision с ключом offer.verification.v1 содержит offerId/versionId/supplierId/lotId/documentId/receiptId, исходную транскрипцию, текущие поля, вопросы и источники. Чтение metadata связывается по конкретному versionId, а не только document_id/SHA.
5. Автор/время/основание сохраняются в решении и audit. Статус общего document после подтверждения не меняется; отдельный offer.verification_status относится только к поставщику/лоту.

Сохранение выполняется транзакционно под блокировкой тендера и проверкой expectedVersion. Создание предложения, исходной версии, текущей версии, позиций/расходов/решения и аудита не оставляет частично подтверждённого состояния. Ревизия тендера повышается. Для ссылок receiptId/offerId/versionId внутри JSON нет новых SQL FK: принадлежность валидирует сервер; основные FK остаются в существующих таблицах. Это версионированный контракт поверх существующего неизменяемого журнала, без скрытой миграции.

Decimal.js 10.6.0 MIT закреплён напрямую; он уже был установлен транзитивно для dev, теперь доступен production-сборке. precision=60, ROUND_HALF_UP в локальном clone; NUMERIC/суммы/количества — строки, Number/parseFloat в денежных вычислениях не используются. Суммы до 14+6, количества до 12+6; результат умножения сохраняет до 12 дробных знаков. Скидки — до 4 знаков.

Откат ветки не удаляет сохранённые предложения/аудит и не переписывает оригиналы. Объектное хранилище и БД по-прежнему не образуют одну транзакцию; автоматический GC не добавлялся.

## 5. Ограничения и риски

- ZIP — отдельный вопрос ИТ/ИБ, ранее обозначенный в TASK-005B; приём/карантин/AV не включены. Это не блокирует TASK-006 согласно прямому разрешению владельца.
- Ручной перенос оригинальных значений не является OCR/доказанным извлечением. Исходная транскрипция фиксируется при первом сохранении; перед этим её нужно проверить. Исправления далее сохраняются отдельно в текущих версиях.
- Для неполного обязательного состава консервативно блокируется рейтинг и в режиме отдельных позиций. Автоматического распределения добавляемых расходов лота по позициям нет; нужна отдельная методика. Валютных курсов и пересчёта НДС/единиц нет.
- Исходная цена и строки истории/скидок относятся к лоту; актуальная база в режиме позиций — к выбранной позиции, это пояснено в UI. Номер версии — сохранение проверки, а не автоматически созданный этап переговоров.
- Арифметика no_reply и скидок покрыта Jest; экран этапов, создание переговоров/писем/новых стадий и серверная регистрация ответа no_reply относятся к TASK-007 и не начаты. Последняя черновая версия явно показывается как непроверенная, не выдаётся за подтверждённый ответ.
- Аккредитация только читает уже существующий отчёт с явными tender/supplier. Экран/загрузка новых отчётов не добавлялись.
- Старые offer без нового контракта ручной проверки автоматически не мигрируются и не перезаписываются; редактирование требует отдельного разбора и возвращает 409. Старый original receipt, заменённый явной legacy-записью при повторной загрузке, может требовать повторного явного выбора поступления в UI.
- Сравнение вычисляется при чтении; это не закреплённый calculation_run, не подписанный протокол комиссии и не автоматическое определение победителя. При параллельных изменениях модель нужно обновить; закреплённый официальный снимок — отдельный контракт.
- Пагинация длинной истории и нагрузочные испытания не выполнялись. В текущем локальном профиле имя dev-актора на скриншотах отображается вопросительными знаками; UUID и дата явно присутствуют в атрибуции. Профиль пользователя не исправлялся догадками.
- Корпоративные SSO/runtime least privilege/OS-изоляция/AV/backup-restore остаются прежними вопросами пилота. Production data access по-прежнему запрещён прежним DataContext.

## 6. Ручная проверка закупщиком

1. Открыть http://127.0.0.1:5173/tenders, создать тендер, загрузить синтетические КП. Через «Уточнить» создать/выбрать поставщиков. Один и тот же оригинал можно зарегистрировать повторно как отдельное поступление.
2. Нажать «Проверить КП» в карточке либо открыть `/review` и выбрать тендер. При title-only тендере нажать «Создать лот без позиций»; либо использовать уже заданный состав с позициями.
3. Явно выбрать поставщика, лот, оригинал и поступление. Отметить подтверждение контекста. Скачать/открыть оригинал PDF, перенести исходные значения вручную до первого сохранения.
4. Заполнить текущую цену/валюту/НДС/оплату/соответствие, либо цены позиций. Оставить срок неизвестным и сохранить черновик с источником «Документ» и комментарием. Проверить вопрос о сроке.
5. Ввести «7 дней», выбрать «Телефон», указать основание звонка, снова подтвердить контекст → «Сохранить и подтвердить». При отсутствии других проблем статус «Проверено». При наличии другого ручного вопроса он остаётся до отдельного явного снятия.
6. Включить расходы, ввести доставку 10000. «Включено в цену» не должно увеличить итог; «Добавить» увеличит его ровно на 10000; «Не уточнено» делает сопоставимый итог неизвестным. Пустая цена обязательной позиции не становится нулём.
7. Переключить поставщика на другого, использующего тот же оригинал: ранее введённые цена/срок/расходы/источники первого не должны появляться автоматически. Выбрать поступление и ввести собственные данные второго.
8. Открыть «Сравнение». Столбцы — поставщики, строки — показатели; исходная цена не меняется, актуальная/история отображаются отдельно. Отсутствующая аккредитация красная. Проверить лот/позиции и предупреждения при несовместимой базе.
9. Скачать CSV с тем же выбранным лотом/режимом; сравнить суммы/условия/вопросы/источники/авторов с таблицей. Перезагрузить экран проверки и проверить сохранённые значения/источники.
10. На узком экране таблица прокручивается внутри своего блока; форма проверки становится одноколоночной.

Запуск dev preview: из корня рабочей области загрузить tools/enter-workspace.ps1, затем в tender-platform выполнить npm run dev:api и npm run dev:web в двух терминалах. Постоянная Windows-служба не устанавливалась. Фоновые refetch по возврату фокуса/восстановлению соединения не перезаписывают несохранённые правки формы проверки.
