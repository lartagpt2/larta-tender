## 5. Замечания и блокеры допуска

### SQL CHECK и NULL — требуется решение перед применением к текущей БД

В 003 условие synthetic-классификации заканчивается выражением
`classified_ocr_hash ~ '^[a-f0-9]{64}$'`, без явного `IS NOT NULL`.
В PostgreSQL CHECK принимает TRUE **или NULL**. Когда остальные проверки TRUE,
NULL-хеш даёт NULL всему CHECK, поэтому именно SQL constraint не обеспечивает
заявленную обязательность хеша. Аналогично nullable evidence может пройти через length(NULL), поэтому для evidence также нужен явный IS NOT NULL.

Подтверждено безопасным `SELECT` выражения: `nullable_hash_check_can_pass_as_null=true`.
INSERT для воспроизведения не выполнялся. API дополнительно сравнивает хеш с текущим
OCR hash и не разрешает такой записи попадание в корзину; это замечание к защите
на уровне БД, а не утверждение об успешном обходе API.

Предлагаемая минимальная доработка проекта 003:

```sql
AND evidence IS NOT NULL
AND classified_ocr_hash IS NOT NULL
AND classified_ocr_hash ~ '^[a-f0-9]{64}$'
```

Миграцию не редактировал. Требуется согласовать доработку PR #13 (или отдельную
версионированную защиту), обновить SHA и негативный SQL-тест на новой синтетике.
Исходную БД до этого и до репетиции не обновлять. Backup/restore без применения
миграции можно согласовать независимо от этого замечания.

### Особенность существующих данных при restore

В исходной схеме есть `new_offer_versions_require_offer ... NOT VALID`.
Старые legacy версии нужно сохранить, не превращая это ограничение в VALID и не
переписывая цены/связи. После создания dump проверить TOC/порядок восстановления
этого CHECK, restore выполнить полностью с post-data, затем сверить исходные строки
и convalidated. Ошибка restore — остановка; не отключать триггеры/проверки и не
чистить legacy, чтобы «довести» восстановление.

### Копия приложения должна читать только копию файлов

В обычном DataContext OCR roots заданы относительно workspace. Одного изменения
PGDATABASE/STORAGE_ROOT недостаточно для доказательства изоляции preview от
исходных research roots. Для проверки копии подготовить отдельный launcher с
явно внедрёнными Pg repositories на pool копии, cloned FileStore/JobStore и
PgLifecycleRepository с **только cloned OCR roots**. Не запускать обычный entrypoint
с исходными roots и не подключать frontend-прокси к копии без отдельного решения.
Это обычное конфигурирование тестового API, техническая ОС-изоляция не заявляется.

## 8. Последовательность применения к текущей БД и восстановление при ошибке

Только после успешной репетиции, принятого отчёта и **нового явного разрешения**:

1. Согласовать текущую БД, точный commit/SHA, окно, исполнителя и проверенный backup.
   Весь old-code/worker контур остановить; не полагаться только на UI feature flag.
2. Создать свежий согласованный DB+FS backup в остановленном состоянии; повторно
   проверить restore в другом новом контуре, сверить baseline. Не использовать
   старый preflight snapshot как автоматическое разрешение работы с изменившимся source.
3. Применить точную согласованную 003 транзакционно: advisory lock, baseline hashes,
   lock/statement timeout, запись в schema_migrations. Никаких classify/archive/trash
   для существующих 207 кандидатов и никакой автоматической выдачи прав.
4. До включения флага проверить неизменность исходных rows/SHA/FK/OCR/audit и пустые
   metadata таблицы. Затем по отдельному допуску включить новый код/flag, перезапустить
   все writers и провести smoke только на новой согласованной синтетике.
5. Остановиться для приёмки. Конкретные действия со старыми кандидатами — другая заявка.

Если миграция падает до COMMIT — штатный ROLLBACK, без обхода constraints и без
обновления baseline/SHA «под результат». При lock timeout не продолжать частичный upgrade.
Если ошибка найдена после COMMIT — остановить writers, сохранить состояние/логи,
не делать DROP/down/TRUNCATE и не запускать старые OCR writers. Предпочтителен
forward fix после отдельного согласования. Аварийное восстановление — из проверенного
backup в **ещё одну новую БД и новый storage**, проверка SHA, затем согласованное
переключение приложения. Повреждённую/исходную БД не перезаписывать и не удалять.

Если после backup уже приняты новые рабочие данные, простое переключение к старому
снимку их потеряет: требуется отдельная сверка/перенос послеbackup изменений и решение
владельца. Потеря данных или автоматическое отключение immutable audit не допускаются.
