## 4. Изменения схемы и данных

- Подготовлена, **не применена** [002](../infra/migrations/002_domain_foundation.sql).
- SHA256 предложения: `896f8133b5f09da8e6fadc650c71d81165c115a6e6ad095df1279619f93e8764`.
- Существующая `postgres/tender_app` не изменялась в TASK-003. Ранее применённая 001 не редактировалась и повторно не запускалась. Выполнялся только просмотр метаданных схемы на предыдущей части TASK-003.
- SQL меняет существующие статусы документов и добавляет NUMERIC-представления старых minor units; допущения требуют ревью. Старые версии без достоверной связи с лотом сохраняются без выдуманного offer_id.
- Инициализация пустой БД транзакционная: 001+002 и журнал checksum. Непустая БД отвергается; runner не обновляет существующую postgres и не создаёт базы/роли.
- Откат до COMMIT — ROLLBACK всей инициализации. После COMMIT: только согласованная замена одноразовой тестовой БД или отдельная номерная forward fix миграция с backup/restore. Автоматического удаления схемы и отключения защит истории нет.

## 5. Расхождения с заданием, риски и долги

- Не закрыты два условия приёмки: человеческое ревью миграции и воспроизводимость на согласованной пустой PostgreSQL БД. DDL/FK/триггеры и реальная конкурентная запись пока не проверены сервером.
- Добавлены минимальные API создания/чтения тендеров и чтения лотов. Остальные бизнес-маршруты DOMAIN_API остаются проектом последующих задач; полный CRUD всех сущностей не заявлен.
- Модель не содержит корпоративного tenant_id: граница организации/SSO и выдача ролей требуют решения ИТ. Текущий адаптер — один серверный dev-actor, отключённый в production.
- Нет workflow записи offer/field decision/cost component и разрешений buyer/manager на него. Введённые роли сейчас применяются только для чтения членами тендера; новые тендеры принадлежат своему создателю.
- Владельцы БД/суперпользователи могут отключить триггеры; необходимы отдельные migration/runtime роли. Правки статуса/ассоциации документа должны проходить через будущий аудируемый сервис.
- OfferVersion и существующие строки OfferItem/CostComponent защищены от UPDATE/DELETE; добавление дочерних строк к старой версии ещё не запрещено. Полная защита закрытого ценового агрегата — отдельная доработка перед бизнес-записью.
- Сопоставление offer_package с одним Offer/лотом и перенос minor units делением на 100 требуют подтверждения. Существующие specification_item/comparison сохранены без автоматического переноса.
- Идемпотентность — внутренняя транзакционная функция одного документа. Загрузка байтов, безопасность архивов, канонизация запроса, ответы при другом ключе для тех же байтов и идемпотентность пакета ещё не реализованы.
- Промышленная политика backup/restore, корпоративный SSO и утверждение CI остаются решениями ИТ. Изоляция ОС ранее отложена пользователем; техническая песочница не заявляется.
