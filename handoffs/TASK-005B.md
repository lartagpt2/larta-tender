- `PATCH /api/tenders/:id/offers/:documentId/association`: прежний вариант `{revision, supplierId, note}` поддерживается. Новый вариант: `{revision, newSupplier:{name, registrationNumber?, email?, comment?}, note}`. Ровно один вариант цели; одновременное указание supplierId/newSupplier или отсутствие обоих — 400. Явный supplierId=null по-прежнему снимает связь. В ответ добавлен supplierId.

- `POST /api/tenders/:id/offers/batches`: прежний формат и лимиты сохранены; optional `X-Tender-Stage-Id` допускает только существующий этап этого тендера. Этап включён в хеш идемпотентности. Без заголовка прежний хеш не меняется, старые ключи остаются совместимыми.

### Решение без миграции

В исходной модели blob/document дедуплицируются, upload_batch фиксирует операцию и автора/время, но повторный документ был связан только с первым batch_id. audit_event прежнего пакета хранил лишь hash манифеста, поэтому не позволял восстановить отдельные файлы повторной отправки. Исходная модель сама по себе не удовлетворяла полной истории поступлений.

Использован существующий неизменяемый журнал field_decision с отдельным версионированным ключом `offer.received.v1`. Это запись подтверждения приёма загруженного файла, а не результат извлечения/распознавания и не утверждение о поставщике. В value сохраняется JSON с batchId, индексом файла/части, logical source, stageId/null, supplierId/null, senderEmail/null, originalName, parentId/null, legacy. Автор и дата — штатные decided_by/decided_at. В той же транзакции добавляется audit `offer.received`. Триггеры 002 уже запрещают изменение/удаление решений. Существующий индекс по document_id обслуживает выборку истории.

Значения batch/stage/supplier задаются сервером после проверки доступа/принадлежности, а не произвольным JSON клиента. Внутри value нет отдельных SQL FK: это осознанный компромисс существующего общего журнала ради минимального изменения без DDL. Контракт ограничен ключом версии; при росте нагрузки можно отдельно предложить нормализованную таблицу поступлений/индексы с миграцией и разрешением владельца.

Первый известный приём legacy-документа показывается из его первоначальных метаданных. При первой новой отправке он сохраняется в журнал перед новым фактом приёма, с исходной датой и автором и пометкой legacy. Поставщик первоначального legacy-поступления не восстанавливается из текущей изменяемой связи: он явно неизвестен. Неизвестные прежние повторные отправки не выдумываются; UI сообщает о неполной ранней истории.

Создание поставщика использует supplier/tender_supplier, отдельное решение `supplier.created.v1`, затем прежнее `offer.supplier` и audit. Комментарий сохраняется в ручном решении; он не добавлен в исходные документы. Оригинальные SHA/байты/имена/MIME/заявленный From и история цен не меняются.

Откат кода не удаляет накопленные факты и поставщиков. Бинарники остаются в прежнем локальном FileStore; атомарной транзакции файловой системы с БД и автоматического GC по-прежнему нет.

## 5. Ограничения и вопросы ИТ/ИБ

### ZIP — явный блокер и предлагаемое решение

Требование задания: «До реализации согласовать с ИТ/ИБ возможность хранения недоверенных архивов без распаковки и политику антивирусного сканирования/карантина». Общие прежние разрешения на разработку не заменяют эту конкретную политику. Вопрос пользователю задан; подтверждения не получено. Поэтому приём остаётся выключенным, UI объясняет причину.

Для отдельного согласования предлагается: отключённый по умолчанию режим хранения opaque ZIP; отдельный карантин внутри утверждённого хранилища; проверка MIME/расширения/сигнатуры и транспортных лимитов; состояние received_unprocessed/quarantined; запрет распаковки/просмотра; AV-проверка по политике ИБ; выдача оригинала только после разрешённого результата сканирования либо иного явно утверждённого правила. Потребуются решения: кто разрешает приём, какой AV/шлюз, поведение при недоступности сканера, можно ли скачивать несканированный файл, сроки хранения и удаления карантина. В этой доработке такой режим не включён и не объявлен безопасным для продукции.

### Массовая привязка — предложение, без неявных изменений

Общий документ может быть вложением нескольких писем/поступлений от разных поставщиков — это подтверждено тестом. Простая массовая смена supplier_id по document_relation затронула бы также общий оригинал в другом контексте. Сейчас «Уточнить» явно изменяет только выбранный документ; UI сообщает это.

Предлагаемая отдельная доработка: выбирать конкретное поступление/письмо, показывать preview точного списка файлов и текущих revision, давать явный checkbox массового подтверждения; связывать решение с конкретным receiptId и сохранять отдельное append-only решение для каждого участника, проверяя весь список атомарно. До согласования этой семантики массовая привязка не добавлена. Цены/offer_version не затрагиваются.

### Остальные границы

- Duplicate warning охватывает поставщиков данного тендера; глобальные/чужие записи не раскрываются. Одинаковые имя/email не приводят к автоматическому объединению.
- From — заявленные данные письма, не аутентификация. В receipt сохраняется разное происхождение одинаковых байтов; текущая группировка оригинала определяется последним явным решением по документу. Для неоднозначных поступлений смотрите историю.
- Возможности EML остались прежними: ограниченный MIME/base64, без общего RFC-парсера, без OCR/LLM/отправки почты.
- Продуктивные SSO, антивирус, OS-изоляция, объектное хранилище, фоновый обработчик и пагинация не добавлялись. Производственный допуск не заявляется.
- Новых зависимостей, MCP, служб, изменений PATH/реестра/PostgreSQL-конфигурации нет.

## 6. Ручная проверка закупщиком

1. Открыть http://127.0.0.1:5173/tenders, создать тендер без поставщиков. ТЗ необязательно.
2. Загрузить несколько разных синтетических PDF/TXT. Нажать «Уточнить» у одного → «Создать нового поставщика». Указать только наименование и основание, оставить email/номер/комментарий пустыми → «Создать и привязать».
3. Перезагрузить страницу: проверить группу поставщика, подтверждённую связь и пустой заявленный From; оригинал скачивается без изменений.
4. У другого файла создать отдельного поставщика с тем же именем: появляется предупреждение о совпадении. Создание требует явного подтверждения; записи не объединяются. При желании выбрать существующего поставщика вместо нового.
5. Проверить необязательные номер/email/комментарий. Email нового поставщика не должен подставляться в From оригинала.
6. После успешной загрузки снова нажать «Загрузить КП»: это повтор той же операции, история не растёт. Нажать «Новое поступление этих файлов»: у оригинала добавляется один факт, сам файл остаётся один. Перезагрузить и раскрыть «Поступления».
7. При наличии этапов выбрать «Этап поступления» и повторить новую отправку: история показывает выбранный этап, старое поступление сохраняет прежний. Если этапов нет — «Этап не назначен».
8. Проверить синтетический EML с вложением и заявленным From. From не обозначает проверенную личность, candidate требует подтверждения.
9. Пока ZIP BLOCKED, загрузить ZIP вместе с допустимым TXT: ZIP отклоняется, TXT сохраняется. Проверку положительного ZIP-приёма выполнять только после отдельной реализации утверждённой политики ИБ.
