### Права и классификация

Видимость сохраняет существующую модель owner/member. Архив и restore требуют
обычного права записи (owner/buyer/manager). Reviewer не меняет состояние.

`trash_synthetic` — отдельная capability на пользователя и тендер: она не
наследуется от owner/manager. `classify_synthetic` отдельно разрешает подтверждение
происхождения или защиту как working. Миграция не выдаёт эти права никому.
HTTP API назначения прав не добавлен.

`unclassified` защищён от корзины. Подтверждение synthetic требует текст evidence
от человека; название/префикс/старый список кандидатов не являются доказательством
и не применяются автоматически. `working` нельзя переклассифицировать в synthetic
через API. Рабочие тендеры можно архивировать и восстанавливать.

Классификация привязана к `content_revision` и SHA списка файловых OCR. Новые
документы, поступления, цены, этапы, SQL OCR или изменённые файловые drafts/reviews
требуют повторного подтверждения синтетики. Все результаты OCR остаются прежними
неподтверждёнными черновиками; данная задача не подтверждает цены/поставщика.

### Preview и конкуренция

Preview возвращает ID/title, бизнес-revision, dependency/content revisions,
счётчики прямых/косвенных связей, число shared SHA, SQL runs, файловые jobs с SHA,
права, ограничения и разрешённые действия. `previewHash` связывает весь снимок.
Перед записью сервер повторяет расчёт под `FOR UPDATE` родительского tender.
Несовпадение возвращает 409, без частично применённого перехода.

Все прямые tender dependencies и восемь косвенных таблиц защищены DB triggers.
Зависимые записи сериализуются с lifecycle по той же строке tender. Активные
pending/running OCR и queued/processing extraction_run блокируют архив/корзину
и классификацию. SQL deadlock/serialization conflict также превращается в 409.

Файловые create/review/worker mark выполняются через parent-row fence. Он проверяет
установленную схему даже при выключенном UI-флаге. SHA OCR дополнительно защищает
классификацию от изменения файлов вне SQL-транзакции. Старые workers без fence
нужно остановить перед включением, это отдельный шаг deployment-плана.

### Сохранность

Переход меняет только metadata lifecycle и добавляет неизменяемые lifecycle_event
и audit_event. Business revision/первичные цены не переписываются. Оригиналы,
версии КП, receipts, этапы, OCR, audit и общие бинарники сохраняются. Lifecycle audit
содержит исходный снимок, новое состояние, actor, reason и hash; UPDATE/DELETE/
TRUNCATE истории запрещены. У tender запрещено физическое удаление.

Read endpoints и прямые ссылки остаются доступны согласно ACL. Карточка архива/
корзины блокирует редактирование; ссылки на оригиналы ТЗ/КП сохраняют доступ к файлам.
Необратимого удаления и массовых endpoints нет.

### Защитные исключения

F, G, текущий демонстрационный тендер и legacy fixture. Для них запрещены
архив/корзина/классификация. SQL CHECK нельзя обойти capability.
Бинарный legacy key не преобразовывался; исследовательские документы и эталоны
не использовались для этих тестов и не менялись. Модель не вызывалась.

## 5. Риски и границы готовности

- Реализация проверена в новой синтетической среде; проверка upgrade/backup
  на копии существующего контура и допуск текущей БД остаются отдельными шагами.
- OCR scanner ограничен известными roots принятого обследования и текущим
  STORAGE_ROOT. Новый root нужно явно включить перед использованием. Ошибка чтения,
  неизвестный status, symlink/junction, oversized JSON или лимит обхода блокируют
  операцию, а не пропускают зависимости. Это не ОС-изоляция.
- Нельзя запускать старые процессы с новыми lifecycle состояниями. Для новой
  domain-таблицы требуется аналогичный guard и включение в preview; 003 покрывает
  существующую схему 001/002.
- Права используют существующую dev authentication-модель, production access
  остаётся выключенным. Назначения capability должны пройти отдельное согласование.
- Legacy `/tenders` сохранён для совместимости старых потребителей и селекторов
  с LIMIT 100; при включённой функции он отдаёт только Active. Новый основной
  список использует полный серверный `/tenders/lifecycle/page`.
- FK/оригиналы остаются на месте: корзина скрывает тесты, но не освобождает место.
  Автоматического retention/purge/GC нет.
- PR основан на непринятой merge-цепочке существующих feature branches;
  база — TASK-008G, а не main. Ничего из этой цепочки не объединено автоматически.
