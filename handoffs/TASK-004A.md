## 1. Итог

**Готово к ручной приёмке в локальном контуре на синтетическом эталоне.** Текстовый PDF теперь даёт редактируемый черновик с количеством, единицей, номером, страницей-источником и техническими группами. До отдельного подтверждения LotItem не создаются. Подтверждение сохраняет исправления и технические условия в PostgreSQL. Повторные запросы не дублируют состав и не перезаписывают подтверждённые данные.

PDF без текстового слоя возвращает needs_ocr и пустой состав. OCR, Ollama и внешние модели не запускались. Исходный пользовательский ТЗ.pdf **не приложен** к этой постановке; его фактическая обработка не заявляется. Синтетический PDF повторяет семь эталонных артикулов и структуру перечня без контактных данных.

Diagnosis исходной версии 89a18a6: uploadSpecification → FileStore.put → PgScopeRepository.attach сохранял original/blob/audit со status=uploaded; вызова извлечения не было. Существующий загрузчик сохранён, добавлены отдельные операции. Ошибка конкретного пользовательского PDF без его получения не утверждается.

## 4. Изменения схемы и данных

- **Новой миграции нет.** Применённые 001/002 не редактировались/не запускались повторно. Существующая postgres не изменялась.
- Записи только в согласованной larta_test_task003: синтетические пользователи, тендеры, спецификации, извлечения, доказательства, решения и аудит. Автоматической очистки исторических строк нет.
- Производные страницы сохраняются как отдельный JSON blob по SHA256 с documentId, runId, sourceSha, версиями extractor/parser. Ссылка на артефакт — versioned JSON extracted_field, не новая колонка/FK.
- extraction_run, extracted_field и evidence_reference сохраняют исходный результат. nullable confidence не выдумывает степень достоверности.
- Подтверждение создаёт LotItem и append-only FieldDecision/AuditEvent в одной транзакции; исходные PDF/метаданные/blob не обновляются. Количества — NUMERIC и строки в JSON.
- Повторное извлечение до подтверждения создаёт отдельный run; подтверждённый результат имеет приоритет. Уже заполненный/подтверждённый состав не заменяется операцией подтверждения другого черновика.
- Откат кода не требует отката DDL; сохранённые производные и решения остаются в существующей схеме. Не удалять историю обходом триггеров. Orphan blob при сбое файловой/DB-операции возможен, GC не реализован.

## 5. Расхождения с заданием, риски и долги

- Исходный PDF заказчика не получен через указанный защищённый канал. Проверен синтетический аналог, поэтому точность именно на пользовательском ТЗ.pdf ещё требует ручного прогона.
- PDF.js Apache-2.0 выбран для локальной реализации; формальное согласование ИТ/ИБ не подменяется этим выбором. Лицензионные ссылки и Node engine указаны в docs/TASK-004A.md.
- Лимиты: 20 МиБ, 30 страниц, 100k символов/страницу, 500k суммарно, 15s, Worker old generation 256 МиБ, 2 active workers/process. V8 limit не равен лимиту всего RSS. ОС-песочница и антивирусная приёмка ещё требуются перед корпоративными файлами.
- В worker не передаются секреты БД/API, только SystemRoot и workspace TEMP/TMP. fetch/eval/fonts/WASM/rendering отключены для server-side извлечения. Это не утверждение об абсолютной сетевой/ОС-изоляции.
- Парсер структурный, ориентирован на нумерованный перечень и шт./шт. Сложные таблицы, произвольные единицы/колонки/порядок чтения и неизвестные технические группы не гарантированы; нужна проверка закупщика и ручной ввод при сомнении.
- Открытие источника использует встроенный PDF viewer браузера; возможность просмотра зависит от браузера, скачивание оригинала остаётся доступным. Иллюстрации не распознаются, исходные страницы сохраняются.
- TXT сохраняет прежний статус ожидания; этот task добавляет именно текстовый PDF. OCR для сканов, пакеты КП, аккредитация и версии предложений не реализуются здесь.
- Корпоративный SSO, least-privilege runtime role, backup/restore и промышленная изоляция остаются вне текущей локальной приёмки. Никаких глобальных пакетов, служб, изменений PATH/реестра/PostgreSQL configuration нет.

## 6. Инструкции для ручной проверки закупщиком

1. Открыть /tenders/new, выбрать «Через ТЗ», загрузить разрешённый текстовый PDF (для автоматического эталона tests/fixtures/tz-seven-items.pdf), создать тендер.
2. Дождаться «Черновик ТЗ готов». Проверить 7 строк и отдельные группы требований; до подтверждения основной состав пуст. Через «Показать фрагмент PDF» сверить страницу-источник.
3. Нажать «Исправить», скорректировать строку/количество/единицу/технические группы, затем «Подтвердить состав». После reload проверить LotItem и доступность режима по позициям.
4. Загрузить тот же PDF повторно: количество позиций, их ID и принятые исправления сохраняются. Новое ТЗ не должно автоматически заменить подтверждённый состав.
5. Загрузить no-text PDF в новом тендере: «Требуется OCR или ручной ввод», окончательные позиции отсутствуют, кнопки ложного подтверждения нет.
6. Для автоматических проверок: загрузить окружение рабочей области, npm run check, затем node scripts/verify-task004a.mjs --run, затем npm run test:e2e. Скрипт требует собранный API и именно larta_test_task003, оставляет синтетические данные. Ручной запуск API/Vite описан в docs/TASK-004A.md.
