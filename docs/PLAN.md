# План разработки корпоративной платформы Larta Tender

Дата: 05.11.2026. План **не является оценкой сроков** и не означает, что интеграции уже работают.

## Конечный пользовательский маршрут

1. Создать тендер: вручную список позиций с количеством, загрузить ТЗ либо ввести только название.
2. Проверить состав лота и выбрать режим определения победителя: по лоту или по позициям.
3. Одним полем загрузить сразу весь пакет КП/писем/архивов разных поставщиков. Позднее можно добавлять файлы.
4. Система регистрирует файлы, извлекает поля, осторожно группирует документы по контрагенту; закупщик разрешает неоднозначности и недостающие данные (включая сведения по телефону).
5. В «Документах» прикрепить отчёты аккредитации из отдельного ресурса, отметить статус и дату.
6. Получить транспонированную сравнительную таблицу: поставщики в столбцах, параметры в строках; дополнительные затраты по явному включению.
7. В «Переписке и этапах» сформировать черновики на уточнение/2-й, 3-й этап/переторжку с адресатами и комментариями.
8. Загрузить ответы, сохранить предыдущие цены, отобразить новую цену дополнительной строкой **той же таблицы**, посчитать скидку. Отсутствие ответа не меняет цену.
9. Подготовить проект заключения с доказуемыми источниками, экспортировать и передать на человеческое согласование.

## Принципы реализации

- Модульный монолит NestJS + PostgreSQL, отдельный асинхронный локальный обработчик документов / Ollama, Vue-клиент.
- Источник истины — исходный файл, проверенные значения и формулы; модель предлагает данные, но не утверждает цену и победителя.
- Файлы хранить в корпоративном хранилище с контролем доступа и контрольной суммой. PostgreSQL хранит метаданные, версии, ссылки, историю. Физический путь хранения, backup, retention и допустимое расположение уточняет ИТ.
- Миграции только версионируемые; операции не должны уничтожать существующую схему/данные.
- Бизнес-логика расчётов — тестируемый backend, не исключительно фронтенд.
- Аутентификация/RBAC/аудит для корпоративной эксплуатации; прототип на синтетических данных до согласования ИБ.

## Поэтапная демонстрация

**Demo A — после TASK-004.** Создание тендера тремя способами, перечень позиций, галка выбора по лоту/позициям, пропуск ТЗ.

**Demo B — после TASK-005.** Пакет нескольких КП одним вводом, повторная загрузка, группировка документов с раскрытием и списком email, ручное разрешение неясных контрагентов.

**Demo C — после TASK-006.** Реальная (не демонстрационно зашитая) транспонированная таблица, ручное подтверждение, учёт логистики/таможни по галочке, сверка валют и единиц.

**Demo D — после TASK-007.** Отчёты аккредитации, красные «Нет проверки», исторические цены всех этапов, проценты скидки, адресованные черновики.

**Demo E — отдельно после решения по Ollama.** Извлечение из PDF/XLSX/DOCX/сканов с точными ссылками на документ, страницу/ячейку, человеком в контуре, метриками качества. До этого момента интерфейс показывает «Ожидает обработки» и не имитирует реальный OCR.

## Согласовать до начала программирования за пределами TASK-001

1. GitHub URL, корень тендерного проекта, текущие ветки и правила PR; не брать адрес репозитория другого проекта.
2. Границы Windows-песочницы (из предыдущей постановки: `D:\ai_projects`; проверить фактические ACL и путь), разрешённые MCP и сетевые направления.
3. Выделенную **тестовую** БД PostgreSQL с минимальной ролью и порядок миграций/backup. Никаких production-доступов.
4. Хранилище исходных файлов, ограничения размеров, антивирусную проверку, хранение/удаление, права доступа.
5. Способ аутентификации, роли: закупщик, руководитель закупок, проверяющий, администратор (согласовать состав).
6. Правила определения сравнимой итоговой цены: валюта, курс и дата, НДС, единицы измерения, стоимость доставки, частичная комплектация, учёт включённых затрат.
7. Форматы реальных документов и допустимость их обработки в локальной системе.

## Критерий завершения MVP

Требования из `docs/ACCEPTANCE.md` выполняются на синтетических данных и подтверждены закупщиком; есть traceability «файл → извлечение → ручное подтверждение → версия расчёта», PR-review, отчёт тестов, OpenAPI, инструкция запуска, план backup/restore, положительное решение ИТ/ИБ для корпоративного пилота.
