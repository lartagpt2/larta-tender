# TASK-004: тендер, ручной состав и оригинал ТЗ

## Реализованный сценарий

Локальная рабочая среда: http://127.0.0.1:5173. Список читает реальные API, показывает до 100 последних доступных тендеров и поиск по названию. Создание тремя путями: название, ручной состав (до 100 строк), название + файл ТЗ. После сохранения открывается S03 выбранного тендера. Карточка также доступна из списка.

Ручные позиции хранятся в одном основном лоте с количеством NUMERIC(18,6), строковым представлением в JSON и отдельной единицей. Запятая в браузерной форме нормализуется в точку без преобразования через Number. Состав можно редактировать, пока не появились предложения поставщиков; тендеры с несколькими лотами этим редактором не переписываются. При конфликте версии требуется обновление карточки.

Режим по позициям недоступен без состава, причина видна в UI и проверяется сервером. Выбранный режим, позиции и флаг пропуска ТЗ переживают перезагрузку. В localStorage остаётся только тема, бизнес-данные туда не записываются.

## Техническое задание

Поддерживаются PDF с проверкой сигнатуры и TXT с валидным UTF-8 без NUL, от 1 байта до 20 МиБ. Файл сохраняется в локальном content-addressed хранилище; БД хранит blob, неизменяемый документ и аудит. Скачивание оригинала проверяет доступ, SHA256 и отдаёт attachment с nosniff, без встроенного просмотра.

Обработчик ТЗ не настроен: OCR/LLM не запускаются. Документ имеет status=uploaded и показывается как «Ожидает обработки»; из загруженного текста не создаются и не подтверждаются позиции. Поэтому ветка UI подтверждения результата OCR не подменяется фиктивной кнопкой. Ручной состав и оригинал ТЗ независимы.

«Пропустить и свернуть» сохраняет specification_skipped и оставляет «Загрузить ТЗ позже». Раскрытие не теряет уже сохранённые файлы/позиции. Загрузка сбрасывает пропуск. Раздел КП доступен независимо от ТЗ; общая мультифайловая загрузка КП относится к TASK-005 и здесь не реализуется.

Загрузка использует UUID Idempotency-Key и канонический hash (байты, имя, MIME, purpose). Повтор того же запроса возвращает тот же документ, конфликт ключа — 409. Одинаковые байты с новым ключом в одном тендере возвращают существующий оригинал, сохраняя его исходное имя и единственный аудит загрузки. Дисковый blob может остаться без строки БД при последующем конфликте/ошибке; автоматического удаления оригиналов нет, GC не реализован.

## API

| Метод | Путь                                     | Результат                                                                               |
| ----- | ---------------------------------------- | --------------------------------------------------------------------------------------- |
| POST  | /api/tenders                             | Название + optional creationMode/ручные items; ручной состав и аудит в общей транзакции |
| GET   | /api/tenders/:id/scope                   | Состав, revision, scopeStatus, selectionMode, specificationSkipped                      |
| PATCH | /api/tenders/:id/scope                   | revision обязателен; обновление состава/режима/пропуска с аудитом                       |
| GET   | /api/tenders/:id/tz                      | Реестр ТЗ без внутренних путей хранения                                                 |
| POST  | /api/tenders/:id/tz                      | Один multipart file, PDF/TXT; UUID Idempotency-Key обязателен                           |
| GET   | /api/tenders/:id/tz/:documentId/original | Оригинальные байты как attachment после проверки доступа                                |

Чтение — owner/member; изменение — owner/buyer/manager. Reviewer получает 403 на запись; чужой ресурс — 404. Запись блокирует строку тендера и проверяет revision, роль участника удерживается FOR SHARE в транзакции. Количества проверяются на сервере, неизвестные/null/лишние поля отклоняются. Ошибки сохраняют correlationId и не включают SQL/файлы/секреты.

## Локальная настройка и проверки

Используется только явно согласованная larta_test_task003. Применены неизменённые 001 и 002 из TASK-003; новой DDL-миграции для TASK-004 нет. Существующая postgres не изменяется. В игнорируемом .env настроены тестовая БД, синтетический app_user, отдельный случайный DEV_API_TOKEN и STORAGE_ROOT внутри рабочей области. Пароль PostgreSQL не используется как API-токен.

Vite слушает только 127.0.0.1 и добавляет токен к upstream API на сервере прокси. Токен не передаётся через VITE_* и не включается в клиентский bundle. Это доверенная локальная среда одного dev-закупщика, не production SSO. Промышленный доступ к данным по-прежнему запрещён фабрикой приложения.

```powershell
. C:\Users\oalimova\ai_project\tools\enter-workspace.ps1
Set-Location C:\Users\oalimova\ai_project\tender-platform
npm run check
node scripts/verify-task004.mjs --run
npm run test:e2e
```

Перед интеграционным скриптом требуется собранный API. Скрипт разрешает запись только в larta_test_task003 с совпадающим ledger checksum 002; синтетические данные остаются для проверки. Playwright запускает собственные серверы, поэтому перед ним остановить свои локальные dev-процессы. Для ручного просмотра запустить npm run dev:api и npm run dev:web в двух терминалах с загруженным окружением.

Ограничения перед реальными документами: корпоративная аутентификация, runtime-роль с минимальными привилегиями, согласованное сканирование антивирусом/ИБ, backup/restore. Архивы, DOCX/XLSX, распознавание и массовая загрузка не принимаются этим endpoint. Пользовательские исходники и документы внешним моделям не отправлялись.
