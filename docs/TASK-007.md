# TASK-007 — коммерческие этапы, аккредитация, черновики

## Что изменилось

Техническое сохранение (`offer_version.version`) и коммерческий этап (`tender_stage.ordinal`) — разные сущности. Ручное сохранение полей КП создаёт техническую версию. Коммерческая цена меняется только после отдельной фиксации ответа с конкретным `offer_version_id`, принадлежащим тому же тендеру, предложению поставщика, лоту и этапу.

При создании первого этапа фиксируются базовые версии уже подтверждённых предложений без этапа. Последующие технические правки не меняют эти ссылки. Для позднего участника есть отдельная явная фиксация подтверждённой базовой версии без этапа: она действует с текущего этапа, не заполняет прошлые этапы задним числом и запрещена после уже записанного ответа. Отсутствующая базовая цена остаётся неизвестной, не превращается в ноль и не участвует в ранжировании.

Этапы создаются последовательно, номер уникален в тендере; типы: уточнение КП, следующий этап, переторжка. Для следующего этапа обязателен комментарий. Типы можно чередовать произвольно. Изменения/удаления уже созданных этапов и зафиксированных ответов через API отсутствуют. Для исправленного коммерческого предложения создаётся следующий этап с объяснением. Запись ответа в более ранний этап после ответа в позднем запрещена.

## Ответы и расчёты

1. Загрузить ответный документ общим загрузчиком, выбрав коммерческий этап.
2. В проверке КП явно выбрать поставщика, лот, оригинал и поступление. Общий SHA документа не переносит подтверждённые значения между поставщиками.
3. Сохранить и подтвердить поля. У версии сохраняется этап выбранного поступления.
4. На странице этапов отдельно выбрать подтверждённую техническую версию и зафиксировать ответ. Версия с нерешёнными вопросами или несопоставимой стоимостью не допускается как подтверждённая цена этапа.

Для каждого этапа в существующей транспонированной таблице добавляются строки цены, скидки этапа, общего снижения и статуса ответа. CSV строится из той же серверной модели. Расчёты используют существующий Decimal, без преобразования денег в JavaScript Number.

- Получен ответ: используется явно выбранный неизменяемый снимок версии.
- Нет ответа: отдельная запись `no_reply`, ссылка на новую версию отсутствует; действует предыдущая подтверждённая цена, скидка этапа 0% при известной предыдущей цене.
- Ответ ещё не зафиксирован: отдельный статус ожидания; предыдущая цена сохраняется, скидка не объявляется нулевой.
- Предложение отозвано: действующей цены и места нет; отсутствие ответа позднее не восстанавливает отозванную цену.
- Разные валюты/базы НДС: процент не рассчитывается; повышение цены даёт отрицательное снижение; нулевой знаменатель — неизвестный процент.

Исходная цена документа и техническая история относятся к лоту. Цена/скидка этапа в режиме позиций относятся к выбранной позиции. Общий процент этапа по позиции неизвестен, поскольку неизменяемая исходная транскрипция хранит общую цену документа, а не исходные цены каждой позиции. Строка общего снижения лота сохраняет прежний смысл. Затраты лота не распределяются по позициям автоматически.

## Аккредитация

Отдельная страница и ресурс загрузки PDF/TXT до 20 МиБ. Пользователь явно задаёт поставщика, дату оценки, статус, название источника/подразделения и примечание. Каждое сохранение добавляет `accreditation_report`, старые строки не обновляются. Оригинал скачивается с проверкой доступа; в истории показаны дата оценки, дата записи, автор, исходное имя и SHA-256. Действующий статус берётся по максимальной дате оценки, затем времени записи.

Одинаковый оригинал может быть связан с несколькими отчётами и компаниями, но статус выбирается исключительно по `(tender_id,supplier_id)`. Без отчёта сравнение показывает красный «Нет проверки».

Существующая схема допускает только `document.purpose=offer/specification`. Чтобы не применять новую миграцию без отдельного разрешения, ресурс использует прежнее хранилище оригиналов с техническим `purpose=offer`, отдельным пакетом и **неизменяемой записью роли** `field_decision/accreditation.file.v1`. Такие файлы не являются поступлениями КП и не видны в реестре КП/проверке. Изменение ассоциации поставщика не меняет роль. Если те же байты позднее явно загружены общим загрузчиком как КП, появляется новое настоящее поступление; загрузка отчёта не выдаётся за прежнее поступление КП. Это совместимый адаптер текущей схемы, а не новая модель `purpose`.

При повторе ключа загрузки совпадение SHA/имени/типа возвращает прежний документ; конфликт даёт 409. Байты хранятся локально content-addressed. Ошибка после записи байтов может оставить невостребованный blob; автоматическое удаление оригиналов не добавлялось.

## Контакты и черновики

Адрес подтверждается закупщиком отдельно для поставщика с документом-источником, основанием, автором и временем. Адрес из распознавания или ручного создания компании не становится подтверждённым автоматически.

Получатели черновика выбираются только по ID подтверждённых контактов этого поставщика в этом тендере с документом-источником. Неизвестные, неподтверждённые и чужие контакты отвергаются. Без email список получателей пуст и это явно видно. Пользователь может редактировать тему/текст и выбирать подтверждённые контакты. Для каждого типа этапа предлагается редактируемый шаблон с названием тендера и комментарием этапа.

Каждая редакция — новая строка `draft_message`, старый текст и адресаты сохраняются. Связь с предыдущей редакцией и ID контактов записаны в audit; повторное редактирование уже замещённой редакции даёт 409. В UI для неё отображается отметка о новой редакции. Все строки имеют `approval_status=draft`; SMTP, отправляющих endpoints, очередей и автоматической отправки нет.

## API

Все маршруты ниже имеют префикс `/api/tenders/:id`. Существующие dev token/RBAC сохранены: owner/buyer/manager могут писать, reviewer читает, посторонний получает 404. Тела записей требуют `expectedRevision`; конкурентная устаревшая запись даёт 409. Загрузка файла использует `Idempotency-Key: UUID`.

| Метод | Путь                             | Назначение                                                                                                   |
| ----- | -------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| GET   | `/stages`                        | Этапы, базовые ссылки, ответы/основания, контакты, история черновиков/отчётов, последние 500 событий журнала |
| POST  | `/stages`                        | Тип, название, комментарий, автоматический следующий номер                                                   |
| POST  | `/stages/baseline`               | `offerId`, `versionId`, `note`: явная база позднего участника                                                |
| POST  | `/stages/:stageId/responses`     | `offerId`, `status`, `versionId` только для received, `note`                                                 |
| POST  | `/contacts/confirm`              | `supplierId`, `email`, `documentId`, `note`                                                                  |
| POST  | `/stages/:stageId/drafts`        | `supplierId`, `contactIds`, `subject`, `body`, необязательный `previousId`                                   |
| POST  | `/accreditations/files`          | multipart `file`, PDF/TXT; запись файла не меняет ревизию тендера                                            |
| POST  | `/accreditations`                | `supplierId`, `documentId`, `assessedAt` ISO, `status`, `source`, `note`                                     |
| POST  | `/offers/batches`                | Прежний общий загрузчик: `X-Tender-Stage-Id` связывает новое поступление с этапом                            |
| GET   | `/comparison`, `/comparison.csv` | Прежние маршруты с коммерческими строками этапов                                                             |
