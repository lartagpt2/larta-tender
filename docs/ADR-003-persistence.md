# ADR-003: PostgreSQL repositories and explicit SQL migrations

Status: proposed for human review. TASK-003, 2026-11-06.

## Decision

Keep the existing SQL baseline [001](../infra/migrations/001_initial.sql) unchanged. There is no existing ORM; use the pinned `pg` driver and explicit, parameterized SQL repositories. Do not introduce a second schema authority or generate destructive ORM synchronization.

Money and quantities use NUMERIC. Node receives NUMERIC and BIGINT as strings; no global type parser and no Number conversion. The API foundation does not perform monetary calculations. UUIDs are generated by Node. Schema-qualified queries avoid dependency on search_path.

Tender creation and its audit event commit together. Reads filter owner/member in SQL; inaccessible IDs return 404. All members may read; creation makes the configured actor the owner. Further write workflows must check buyer/manager permissions and lock the authorization row in their transaction. No such workflow is exposed yet.

## Compatibility

[002](../infra/migrations/002_domain_foundation.sql) extends the existing twelve tables and introduces the domain tables in [ERD](./ERD-TASK-003.md). Existing title-only tenders stay valid. Owner backfills from created_by. Existing monetary minor units are copied into NUMERIC by division by 100; this assumption must be reviewed before upgrading any populated database. Original minor-unit columns remain untouched.

Existing offer versions cannot be assigned a lot reliably. Their new offer/lot fields remain NULL; a NOT VALID constraint preserves these rows while requiring offer and lot on all new versions. No inferred suppliers, stages, or timestamps of commercial responses. Document statuses map recognized → extracted, review → needs_review, error → failed. These persisted values are an API compatibility change.

One legacy offer_package maps to one new Offer. The package and offer supplier/tender must match. Supporting a single package across several lots would require a reviewed change to this mapping. A stage response is separate from a price version: no_reply cannot create a new version. Accreditation requires an original document; absence of a report remains absence, never an assumed successful check. Repeated extraction runs get separate field uniqueness, and unknown confidence may be NULL.

## Immutability and idempotency

Triggers block UPDATE/DELETE/TRUNCATE of audit events, offer versions, receipts, field decisions, blobs and price-component rows. Document identity, original metadata, uploaded author, timestamp and blob cannot be changed; document deletion/truncation is blocked. Mutable association/status is distinct from the original and needs audited application workflows in future tasks.

These triggers do not protect against a database owner/superuser. IT must provide a separate migration owner and least-privilege runtime role before production. Child offer_item/cost_component rows cannot be modified but can still be appended: a sealed aggregate and complete business write service are future work. Do not claim complete snapshot protection against direct privileged SQL.

A receipt claims (tender_id, request_key) using INSERT ON CONFLICT DO NOTHING. Under READ COMMITTED the loser waits for the winner, then a fresh SELECT reads its receipt. A different canonical request hash is 409. Receipt and original/audit must share one transaction; the deferred FK rejects a dangling receipt. Callers must authorize first and hash all relevant normalized request fields, not only file bytes. A different key for identical bytes is still subject to the original document uniqueness constraint. Full upload, byte validation, deduplication responses and batch idempotency belong to later tasks.

## Migration and recovery

[Runner](../scripts/migrate-empty-test.mjs) previews without connecting. Apply requires an explicit `larta_test_<name>` database and the exact reviewed 002 SHA256; system/shared `postgres` is rejected. The runner checks an unchanged 001 checksum, rejects nonempty databases, serializes its own executions, runs 001 and 002 in a single transaction and records hashes. It does not create a database, grant permissions, install an extension or seed actors. A second apply is rejected because the database is no longer empty.

This runner deliberately cannot baseline/upgrade the existing postgres database. For an existing database, first agree backup/restore, compare schema against 001, review populated-row impact, and prepare a separate owner-approved application procedure. The old baseline must never be rerun there.

On SQL failure the entire initialization rolls back. After commit, recovery for this disposable test environment is an owner-approved replacement empty database and rerun. There is no automatic DROP/down migration. For retained data, take a verified backup and use a separately reviewed numbered forward fix. Do not disable append-only triggers to undo business history.

## Runtime access

Default DATA_ACCESS_ENABLED=false creates no Pool and opens no database connection. Development-only API requires a server-side actor UUID already provisioned in app_user and a random token of at least 32 characters from ignored .env. Clients cannot choose an actor. Production forcibly disables this adapter; corporate SSO/RBAC mapping remains an IT decision. This is a local development adapter, not production identity management.

## Verification boundary

Unit/HTTP tests use only synthetic mocks. The real PostgreSQL script [verify-test-db](../scripts/verify-test-db.mjs) is prepared but must run only after approval on a disposable migrated database. Until then SQL syntax, FK behavior, database permissions and actual concurrent transaction behavior are not accepted as verified.
