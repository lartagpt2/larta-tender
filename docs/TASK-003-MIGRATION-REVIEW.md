# TASK-003: пакет согласования миграции

Статус: подготовлен, не применён. PostgreSQL и существующая база `postgres` не изменялись в TASK-003.

## Что согласуется

1. [Миграция 002](../infra/migrations/002_domain_foundation.sql): доменные таблицы, составные FK, NUMERIC, индексы, неизменяемые оригиналы и append-only история.
2. [ADR](./ADR-003-persistence.md): pg вместо новой ORM, совместимость, ограничения и восстановление.
3. [ERD](./ERD-TASK-003.md) и [изменения API](./TASK-003-API-DIFF.md).
4. Отдельная **пустая одноразовая тестовая БД** с именем `larta_test_<имя>`, подготовленная владельцем PostgreSQL. Не использовать существующую `postgres` как пустую тестовую БД.

Ревью: проверить соответствие бизнес-модели, связь package → offer → lot, семантику валют/старых minor units, статусы документов, пределы неизменяемости дочерних ценовых строк. Отдельный runtime-пользователь и корпоративная авторизация нужны до промышленного использования.

## Последовательность после подтверждения человеком

Команды выполнять из корня репозитория после загрузки окружения рабочей области. Скрипты читают секреты только из игнорируемого .env; имя БД задаётся явно аргументом, не берётся из PGDATABASE.

```powershell
. C:\Users\oalimova\ai_project\tools\enter-workspace.ps1
Set-Location C:\Users\oalimova\ai_project\tender-platform
node scripts/migrate-empty-test.mjs
```

Эта команда безопасно показывает SHA256, не подключаясь к БД. После человеческого ревью подставить точное согласованное имя и текущую сумму вместо заглушек:

```powershell
node scripts/migrate-empty-test.mjs --apply --database larta_test_REPLACE --reviewed-sha REPLACE_WITH_REVIEWED_SHA256
npm run build --workspace @tender/api
node scripts/verify-test-db.mjs --run --database larta_test_REPLACE --reviewed-sha REPLACE_WITH_REVIEWED_SHA256
```

Заглушки намеренно не проходят проверку имени/контрольной суммы. Первая команда применяет 001+002 только в пустой БД в одной транзакции, создаёт журнал миграций; вторая проверка записывает синтетические фикстуры в эту одноразовую БД и оставляет их для разбора. Не направлять её на сохранённые пользовательские данные. Проверяются конкурентный приём одного документа, конфликт ключа, запрет изменения оригинала/аудита/версии/блоба, точность NUMERIC и отказ чтения чужого тендера.

Скрипты не создают базу, не выдают права, не создают роль и не меняют конфигурацию PostgreSQL. Роли нужны CONNECT и CREATE в выделенной тестовой БД; промышленную схему прав определит ИТ. При SQL-ошибке инициализация откатывается целиком. После успешного применения повторный запуск отклоняется как непустая БД. См. стратегию forward fix в ADR.

## Отдельное включение API

До успешных интеграционных проверок DATA_ACCESS_ENABLED оставить false. После них согласовать тестовую БД в .env, отдельного заранее созданного app_user и локальный токен. Серверный DEV_ACTOR_ID — это UUID app_user, не имя роли PostgreSQL. DEV_API_TOKEN — отдельный случайный секрет длиной минимум 32 символа; пароль БД для него не использовать.

Это не подключает интерфейс к бизнес-данным. Полный CRUD, бинарные загрузки, распознавание и сравнение относятся к последующим согласованным заданиям.

## Требуемое решение владельца

Подтвердить рассмотрение конкретного текста 002 и назвать созданную пустую тестовую БД, разрешённую для миграции и синтетических интеграционных тестов. После проверки БД можно завершить приёмку TASK-003. Переход к TASK-004 — отдельное согласование.
